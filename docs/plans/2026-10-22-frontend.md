# Frontend implementation plan

Goal: deliver Lane D's complete clickable frontend in apps/web, using the reference MVP's calling workflow and clearly labeled browser-local sample data. No backend implementation, Gemini calls, commits, or pushes.

Architecture: Next.js App Router, React and TypeScript; one persisted workspace managed by a reducer; validated local data; pure CSV parsing and domain operations; simulated research service isolated from presentation. Radix dialogs provide focus management. Auth and real API contracts remain dependent on Lane C.

1. Create application configuration and write behavioral tests for CSV import, state transitions, stale research, and persistence validation.
2. Implement domain operations and demo fixtures. Run node tests.
3. Build calling workspace, list management, selection/search/filter, briefing tabs and evidence, prospect forms, CSV preview, research actions, and on-call mode.
4. Style a compact light sales workspace: neutral surfaces, green actions, clear type hierarchy, compact queue and generous briefing text. Make narrow-screen navigation and modal focus work.
5. Add browser tests for the complete workflow, reload recovery, CSV import, failure recovery, and mobile use. Run type checking and production build.
6. Request independent review, fix actionable findings, sync to the existing frontend/app-foundation checkout, verify there, and leave changes uncommitted and unpushed.

Acceptance: users can create lists, enter/edit/remove prospects, import valid CSV rows with duplicate/error feedback, simulate research, inspect sample sources and uncertainties, connect/end one call at a time, and recover their workspace on reload. User-entered prospect data must never be presented as researched facts. Storage failures must be visible. An outdated job must never overwrite an edited prospect.
